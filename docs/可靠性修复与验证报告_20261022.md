## 问题确认与落地

| 问题 | 基线复现 | 修复行为 |
|---|---|---|
| 历史标签和分隔符未完整计入词数 | 最终上游文本为 6003 词，超过 6000 词上限 | 每次加入历史后计算实际拼接文本；发送前再次核对字符、词数；临界 6000 词和 49500 字符均可放行 |
| 普通对象继承属性被当作模型 | `constructor` 返回 200 并触达模拟上游 | 查找前检查自有属性，映射值必须是非空字符串；特殊属性名返回 404 |
| 非文本块被静默过滤、错误结构未校验 | 无效内容类型可能返回 200 或 500 | 四协议转换前校验 JSON 对象、消息数组、角色、内容块和文本类型；畸形输入为协议化 400，不支持的内容沿用 422 `not_supported` |
| 历史裁剪只写日志 | 客户端缺少裁剪标记 | 四协议的流式和非流式响应均附 `X-Context-Truncated: true/false`，并通过 CORS 暴露 |
| 总超时从排队后计算 | 排队加生成超过预算仍返回成功 | 计时覆盖请求体读入、会话等待、并发排队、响应头和正文；持续心跳不延长总期限 |
| `message_start` 就更新会话 | 失败轮的 assistant ID 成为下一轮 parent | `message_start` 仅暂存候选，完整 `end_turn` 成功后提交；失败、取消、异常 EOF、输出裁剪均保留上个完成检查点 |
| 同会话并发读取旧 parent | 并发第二轮未携带第一轮完成后的会话 | 先获得同会话串行锁，再读取检查点并更新上游请求；不同模型复用同一会话返回本地 400 `session_model_mismatch` |

模型窗口标签兼容仅剥离 `[1m]`、`[200k]` 等末尾标签，剥离后的名称仍须登记。Gemini 路径先解码再查找。窗口标签不会扩大上游预算，也不构成模型具备相应窗口能力的承诺。

所有四协议响应均补 `X-Request-ID`，入站拒绝路径也写完成日志。原有 `603 → 400 context_length_exceeded` 契约保留。

## 时限和会话边界

用户确认按默认时限执行。`UPSTREAM_TOTAL_TIMEOUT_MS` 保留默认 180000 毫秒，兼容旧变量 `UPSTREAM_TIMEOUT_MS`，默认预留 1000 毫秒收尾。新增 `REQUEST_TIMEOUT_RESERVE_MS` 可调整余量，余量最多占总预算十分之一。请求约在第 179 秒中止上游工作并返回协议化错误；这表示应用预算，未宣称已核实所有部署平台或前置代理的时限。

同会话串行和检查点仍属于进程内状态，限于既有 OpenAI Chat 的 `X-Session-ID` 复用路径。其他协议仍通过完整文本消息表达历史。多实例协调、跨进程恢复和完整原文持久化不属于本次交付。

## 完整上下文续传：独立交付评估

本轮先完成可靠性缺口。现有链路只有上游会话标识和内存检查点，尚无分片内容被持久保存的明确确认协议；仅凭 `message_start`、普通应答或会话 ID，无法证明完整原文已经登记、重启后仍可恢复或首中尾内容能够召回。因此本次不启用持久化续传，也不将普通 429 表示为已保存的登记进度。

下一阶段应使用独立、低频、限额的真实上游实验，依次验证：

1. 用随机标记区分历史首、中、尾，分片发送后检查确认和跨轮召回，区分模型复述与实际登记能力。
2. 检查会话归属、模型绑定、会话保留时间以及冷启动后的恢复能力。
3. 记录完整原文及其哈希，模拟原文缺失、哈希不一致、重复提交和登记中断，确认不能误推进进度。
4. 统计累计用量、每片耗时及有效上下文成本，再确定分片、批次和请求期限。

只有上述实验提供足够证据，才实现“保存原文 → 确认分片 → 恢复尾部 → 发送新增问题”。该路径需要独立测试、独立发布，不能由本次可靠性回归的成功结果推导其可行性。
