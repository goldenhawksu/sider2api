## 二、关键设计决定

### 1. 成功判定为什么必须双向收紧

旧逻辑 `if (res.ok) recordUpstreamSuccess(model)` 有两个漏洞:

1. HTTP 200 只代表上游**接了单**, 不代表调用成功。sider 大量业务错误 (1135/1101/707/1001) 都是 `200 + SSE code`。
2. 半开探测恰好是这个漏洞的最大受害者: 探测请求先清空账号冷却, 再在 SSE 里读到 1135 —— 等于**用一次失败证明"账号已恢复"**, 下一个请求立刻再撞墙。

新语义由两个独立条件共同决定:

```
结算成功  ⟺ 消费方 complete() 正常读完
          ∧ 读到过内容型事件 (text/file/reasoning_content/tool_call)
          ∧ 没有出现过致命业务码 (1135 / 1101 / 707 / 1001)
          ∧ 本次没有超时
```

`complete()` / `release()` 分离是关键: 中途异常、客户端断开、流空闲超时都走 `release()`, 只释放槽位不计成功。流读完但消费方尚未申报时有一个 5 s 宽限期 (`UPSTREAM_STREAM_END_GRACE_MS`) 兜底结算, 避免槽位挂住。

### 2. 门控学习与客户端响应策略彻底分开

审计指出: 旧实现只在"还没向客户端吐过正文"时才回写门控, 于是"先给正文再报错"的流会让门控完全看不到上游已经撞墙。

现在 `iterateSiderEvents()` 对**每一个** `code !== 0` 的顶层事件都回调 `onBusinessError` → `call.reportBusinessError()` → `noteUpstreamOutcome()`。是否把错误呈现给客户端, 是消费方自己的判断 (例如已输出正文时只记日志继续)。`1101` 这类"正文后的 warning"实测 (`MOCK_WARNING_AFTER_TEXT`) 仍保留正文, 但门控照常学习。

### 3. 三段超时而不是"再加强一下总超时"

```
UPSTREAM_HEADER_TIMEOUT_MS       默认 30 s   从 fetch 到响应头
UPSTREAM_STREAM_IDLE_TIMEOUT_MS  默认 60 s   相邻两个响应体分片之间的最大间隔
UPSTREAM_TOTAL_TIMEOUT_MS        默认 180 s  整段调用生命周期 (兼容旧变量 UPSTREAM_TIMEOUT_MS)
```

三者统一 `AbortController.abort(reason)` + 显式 `reader.cancel()` + `settle()` 释放槽位, 映射为 **504 `timeout_error`**。
`UPSTREAM_SLOT_MAX_HOLD_MS` 的默认值改为"响应头超时 + 总超时 + 30 s"的合计, 保证它只会兜住"连三段超时都没兜住"的意外。

流式端点在响应头已发出后无法再改 HTTP 状态码, 因此这时改为发一条**协议原生的超时错误事件** (OpenAI: error chunk + `[DONE]`; Anthropic/Responses: `error` 事件; Gemini: `error` 载荷) 再关流, 而不是静默断开。

### 4. 统一错误出口的两层结构

```
classifyUpstreamError(code, msg, fallbackMs)   ┐
classifyUpstreamHttpStatus(status, msg)        ├─► UpstreamErrorDetail (与协议无关)
classifyUpstreamHttpError(status, rawBody)     ┘
                       │
                       ▼
        protocolErrorResponse(protocol, detail)      → HTTP 响应
        protocolErrorPayload(protocol, detail)       → 流内事件载荷 (同一份内容, 两个用途)
```

关键规则:

| 上游码 | HTTP | 统一语义 | Retry-After |
|---|---|---|---|
| 603 | 400 | `context_length_exceeded` | 不带 (调用方的问题, 不该引导重试) |
| 1101 | 429 | `rate_limit_error` | 1~5 s (解析上游文案, 默认 2 s), 不做长熔断 |
| 1135 | 429 | `rate_limit_error` | 解析上游文案秒数, 解析不出用模型级兜底 |
| 707 | 503 | `upstream_unavailable` | ~300 s |
| 1001 / HTTP 401 / 403 | 401 | `auth_error` + **账号级鉴权故障态** | — |
| 其他 HTTP 非 2xx | 502 | `upstream_error` | — |

三种协议各自的渲染: OpenAI/Responses 共用 OpenAI 结构; Anthropic 走它的错误类型枚举 (并把统一类型放在 `code` 里保持可机器判别); Gemini 走 `{error:{code,message,status,details}}`。

### 5. 账号级鉴权故障态 (审计阶段三的验收项)

Token 失效时所有模型都会失败, 逐个上游试探只是在烧并发槽。新增 `accountAuthFaultUntil`: 一旦出现 1001 / 401 / 403, 全账号停投 5 分钟 (`ACCOUNT_AUTH_FAULT_MS`), 期内只放半开探测, 任何一次真正成功即解除。

半开探测名额也做了收口: `accountProbeInFlight` + `accountProbeDeadline` 保证"探测还没出结果前不再放第二个", 探测请求**在租约结束时归还名额但不动冷却时长** —— 探测失败时冷却必须继续保持。

### 6. 未知模型: 为什么图像端点网开一面

文本四个端点严格按 MODEL_MAPPING 校验 (P2)。`/v1/images/generations` 保持"未登记即回退 sider": 该端点的 `model` 走的是 OpenAI 图像模型命名空间 (`dall-e-3` / `gpt-image-1` 等), 这些名字本来就不在上游模型表里, 上游 sider 也没有对应条目 —— 在那里套用校验只会让默认参数直接 404。

### 7. 会话复用: 完整历史仍在注入

去掉指纹推导后, 无 `X-Session-ID` 的请求按无状态处理, 但**上下文不会丢**: 每次请求都会把完整历史 (含 system 与当前问题) 通过 `multi_content` 注入上游, 这正是旧实现已有的行为。丢掉的是上游 `cid` 的会话记忆, 换来的是消除"同调用方、同开头、不同对话撞进同一个上游会话"的串话风险。响应头仍会回传本次的一次性 ID, 调用方带上它即可重新启用有状态模式。

## 五、遗留问题与后续建议

1. **进程内队列不跨实例**: Deno Deploy 多实例下 `upstreamQueue` 只保护单实例。审计的建议是"先明确声明单账号容量, 确认存在稳定多实例并发后再考虑 KV 租约", 本次采纳。KV 租约会引入租约过期/网络延迟/脑裂边界, 收益不明确前不做。真正扩容应走多账号池化, 而不是放宽单账号限流。
2. **`smoke` 标记中混有消耗额度的用例**: `test_stats.py::test_stats_reflects_chat_request` 被标记为 `smoke` 但会真实发起一次对话 (1 次上游调用)。这是既有问题, 本次未改动; 建议后续把它迁到 mock 栈。
3. **图像端点的未知模型仍回退** (见二-6), 如需一并收紧, 需要先建立 OpenAI 图像模型命名空间到上游的映射表。
4. **`test/probe_sdk_compat.py` 仍是人工脚本**, 且是仓库中唯一使用 CRLF 的文件 (其余为 LF)。其协议契约已由常驻 mock 用例覆盖, 该脚本可作为"真实环境 SDK 冒烟"保留。
5. **探测器脚本的模型名已同步更新**: `probe_capabilities.py` / `probe_image_models.py` / `probe_tools_deep.py` / `probe_builtin_tools.py` / `bench_models.py` / `probe_sdk_compat.py` 中使用的 `gpt-4.1` / `gpt-5` / `gpt-5.4` / `claude-opus-4.5` / `gemini-2.5-flash` / `gemini-3.7-flash` 均不在 MODEL_MAPPING 内, 在 P2 生效后会 404, 已替换为表内等价模型。
