# 调用 sider 上游的开发规则

> 面向任何要把 sider.ai 当作上游能力源的项目（API 网关、适配器、SDK 封装等）。
> 本文的每条规则都来自 2026-08-31 ～ 09-01 对 sider 上游的实测，标注了**实测**还是**推断**。
> 推断项请自行验证后再依赖。

---

## 零、先理解 sider 上游的本质

sider 的对话接口不是一个为第三方设计的 API，而是**其浏览器插件的私有后端**。这决定了三件事：

1. 请求要伪装成插件形态（`app_name` / `from` / `tz` 等模板字段），**协议会随插件升级而变**；
2. 配额和风控是按「一个人在用插件」的强度设计的，不是按「一个服务在转发流量」设计的；
3. 没有稳定性承诺、没有版本化、没有变更公告。

**推论**：任何基于 sider 的项目都应把上游当作**易变、脆弱、额度稀缺**的资源来对待，而不是当作云厂商 API。下面所有规则都是这个推论的展开。

---

## 一、并发：上游是单并发（实测）

**证据**：10 个并发请求打同一实例，只有 1 个成功；其余返回

```
Your account has an active request - only one request at a time. Please try again later.
```

**规则 1.1**：不要假设上游能并发。设计上默认「同一账号同一时刻只有一个在途请求」。

**规则 1.2**：并发冲突应当**排队**而非**失败**。这些请求通常只要等几秒就能成功，直接返回错误是把上游的限制原样转嫁给了下游调用方。

**规则 1.3（重要）**：如果实现排队/信号量，槽位必须持有到**整个请求周期结束**（含流式传输完毕），而不是响应头到达就释放。上游的 "active request" 覆盖整个流；提前释放会让下一个请求在前一个还在传输时发出，照样撞并发限制。

**规则 1.4**：排队要有上界——最大排队数 + 最长等待时间，超限才返回 429（带 `Retry-After`），否则请求会在队列里堆到客户端超时。同时给槽位加一个「最长持有时间」兜底，防止流悬挂导致槽位永不释放。

**注意**：如果部署在多实例环境（如 Deno Deploy、Serverless），进程内的队列/信号量**不跨实例**。要么接受它只在单实例内有效，要么用外部协调（但 KV 类存储的延迟通常不适合做并发锁）。不要以为加了进程内锁就万事大吉。

## 二、额度：1135 会告诉你要等多久（实测）

**证据**：上游额度耗尽时返回业务码 `1135`，消息里**明确写着恢复时间**：

```
You've reached the current usage limit. This limit ensures fair use for all users.
Please try again after 117 minutes.
```

实测到的时长跨度极大：**1 分钟 / 117 分钟 / 261 分钟 / 272 分钟**。

**规则 2.1（最重要的一条）**：**解析这个时长并按它来退避，不要硬编码熔断时间。**

硬编码会在两个方向同时出错，我们两边都踩过：

| 上游实际说的 | 若硬编码「旗舰模型罚 1 小时」 | 后果 |
|---|---|---|
| `after 1 minutes` | 罚 1 小时 | **白白闲置 59 分钟的可用额度** |
| `after 272 minutes` | 罚 1 小时 | 1 小时后又去撞墙，**反复浪费调用** |

解析建议：正则匹配 `after\s+(\d+)\s*(hours?|minutes?|seconds?)`，解析失败才回退到保守的固定值。

**规则 2.2**：1135 **首先是模型级的**（实测：`claude-opus-4.8` 锁死 272 分钟时，`gpt-5.5`、`deepseek-v4-pro` 完全正常）。所以不要因为一个模型额度耗尽就把整个上游标记为不可用。

**规则 2.3**：但密集调用后，1135 会**升级为账号级**——多个不同模型在短时间内都返回 1135。此时应判定为账号额度池枯竭，停止让请求逐个模型去试探（每次试探都是一发无谓的调用）。判定方式：滑动窗口内命中 1135 的**不同模型数**超过阈值。

**规则 2.4（配套，容易漏）**：账号级冷却**必须有半开探测**——冷却期内定期放行一个请求去试，成功即解除。

否则会陷入死锁：冷却期内所有请求都被拦 → 永远没有成功调用 → 永远等不到「上游已恢复」的证据 → 只能干等到名义到期。我们第一版就是这么写的，等于把「惩罚过度」的毛病从模型级搬到了账号级。

**规则 2.5**：**旗舰模型的额度极其稀缺**。实测 `claude-opus-*` 系列打爆后锁 **4.5 小时**，而 `gpt-5.5` / `gemini-2.5-flash` / `claude-sonnet-5` 等宽松得多。不要把旗舰模型放进任何高频路径（尤其是自动化测试的默认模型集）。

## 三、限速：保护性节流是必须的，且不该固定（实测 + 推断）

**规则 3.1（实测教训）**：一定要在自己这一侧做节流。CLAUDE.md 记录过：高频直连 sider.ai 会触发 **IP 级封禁**（本地直连被阻断 `WinError 10051`，而部署在云上的实例仍正常）。

**规则 3.2（血泪教训）**：**绝不要为了「让测试跑得顺」而关掉自己的限速门。**

我们为消除测试里的限速假失败，把限流开关关了跑全量回归，**三分钟内把上游额度打光**，后续所有测试作废，等了几个小时才恢复。限速门恰恰是防这件事的；关掉它跑测试，等于拆掉保险丝去测电路。

**规则 3.3（推断，我们已实现并在生产验证）**：固定窗口配额与上游真实容量是错配的。上游卡的是**并发**，固定「每分钟 N 次」既可能限得太死（串行客户端每次 3～5 秒，一分钟本可做 12～20 次却被限到 6 次），又拦不住真正的并发冲突。

建议用 AIMD（加性增/乘性减）自适应：连续成功则逐步放宽配额，撞到 1135/1101 则配额减半。我们的生产实测：配额从 6 自适应到 8，第 9 次才拦——相当于每分钟多用出 2 次原本被闲置的额度。

**规则 3.4**：所有 429 响应都要带 `Retry-After`。客户端 SDK（OpenAI/Anthropic 官方 SDK 都是）依赖这个头做退避重试；缺了它，SDK 会退化成固定间隔盲重试，反而加重上游压力。**注意上游透传的 429 也要补这个头**，不能只有自己限速门产生的 429 才带。

## 四、业务错误码语义（实测）

sider 的 SSE 帧顶层有 `code` 字段，非 0 即业务错误。已确认的语义：

| code | 含义 | 正确处置 |
|---|---|---|
| `1135` | 额度耗尽 | 按消息中的时长退避（见规则 2.1）|
| `1101` | 瞬时并发冲突 | **不要长熔断**，短暂避让即可 |
| `603` | 输入载荷过大（实测阈值约 8810～22000 字符）| 返回 400 类错误，**绝不熔断**——这是调用方的输入问题，不是上游故障 |
| `707` | 需短暂停投 | 暂停该模型几分钟 |

**规则 4.1**：**按错误码区分对待，不要「上游返回错误就熔断」。** 把 `603`（用户输入太长）当成上游故障去熔断模型，会因为一个用户的超长输入而让所有人不可用。

**规则 4.2**：网络抖动、5xx 也不应触发长熔断——把一次抖动放大成长时间不可用是得不偿失的。我们的实现里只有 `401/403` 和 `1135` 会熔断。

## 五、流式处理：不读完就必须 cancel（实测 + 推断）

**规则 5.1（实测）**：很多路径会提前结束读流——命中 stop_sequence、收集够图像、达到 max_tokens、遇到错误码。**这些路径必须 `cancel()` 上游的 reader。**

我们审计自己的代码时发现，四个流式处理路径**每个都是 1 处 cancel 对 5～6 处 return**——意识到过问题，但没做全。

**规则 5.2（推断，未验证）**：不 cancel 会让上游连接一直挂着，**上游很可能仍把该请求算作「进行中」**。考虑到上游是单并发（规则 1.1），这可能正在加剧 `only one request at a time` 冲突。

这条我们没能验证——mock 环境只能证明本地资源被释放，证不了上游那边的连接记账行为。但即便不谈并发，泄漏连接本身也该修。

**规则 5.3（实现技巧）**：如果你的 SSE 行读取器是 **async generator**，把 `cancel` 放进它的 `finally`：

```js
async *readLines(reader) {
  try {
    while (true) { /* ... yield 行 ... */ }
  } finally {
    try { await reader.cancel(); } catch { /* 已关闭时忽略 */ }
  }
}
```

JS 保证 `for await` 提前 `break` / `return` / `throw` 时会调用 generator 的 `.return()`，`finally` 必定执行。**一处收口覆盖全部调用点**，比在每个 `return` 前补 `cancel` 可靠得多——后者我们数出来有 21 处，漏一个就是一次泄漏。

## 六、能力边界：不要 fake 上游没有的东西（实测）

实测确认的能力面：

| 能力 | 状态 |
|---|---|
| 文本对话（流式/非流式） | ✅ |
| 推理模式（`-think` 后缀变体） | ✅ |
| 图像生成 | ✅ |
| 多轮会话 | ✅（靠上游会话 id）|
| **视觉输入（图片理解）** | ❌ 不支持 |
| **客户端 function calling** | ❌ 不支持（上游有自己的内置工具，但不接受外部工具定义）|

**规则 6.1**：上游没有的能力，**明确返回标准化的 `not_supported` 错误，不要 fake、不要硬凑**。伪造一个「看起来能用」的 vision 支持，只会让下游在真实场景里拿到胡编的答案。

**规则 6.2**：上线任何新能力前先 probe 上游确认其存在与协议形状。上游协议随插件升级而变，昨天能用的今天可能就变了。

## 七、模型行为差异（实测，影响体验设计）

**流式分块粒度在模型间差异巨大**。同样输出约 200 字：

| 模型系列 | 分块数 | 体感 |
|---|---|---|
| gpt / qwen / llama / kimi / grok | 156～198 块 | 逐字流出，顺滑 |
| glm / sider | 93～154 块 | 中等 |
| **claude / gemini** | **8～13 块** | **一顿一大段，接近伪流式** |

**规则 7.1**：不要假设「开了 stream 就有逐字体验」。如果你的产品对流式体验敏感，要么在模型选择上引导，要么在文档里说明差异。这大概率是上游对不同模型的分块策略差异，不是你能修的。

**性能基线**（15 模型横评，统一 200 字中文写作）：TTFT 中位数 **2.12s**，吞吐中位数 **48.2 字符/秒**。可作为你自己实现的对照——明显慢于这个数就该查自己的转换层。

## 八、测试策略：额度是最稀缺的测试资源

**规则 8.1**：**把门控逻辑测试和上游行为测试分开。**

- 限速、熔断、配额、错误码映射 → **用 mock 上游测**，零额度、可精确控制、结果稳定；
- 只有真正依赖上游真实行为的（比如「什么样的输入会触发 603」）才打真实上游。

我们把三个限速用例从真实上游迁到 mock 后，每轮回归少打 20+ 次上游，覆盖反而更精确（可以固定配额，不受自适应逻辑干扰）。

**规则 8.2**：**测试套件自己会触发限速。** 密集跑测试时，套件会在 60 秒窗口内对同一模型打远超配额的次数，产生大量**假失败**。我们第一轮完整回归 13 个失败**全部**是这个原因，分批重跑后 13/13 通过。

解决办法是按模型/文件分批、批次间等待窗口重置——**不是**关掉限速（见规则 3.2）。

**规则 8.3**：**一轮不过就停下来分析，不要反复重跑。** 我们连跑四轮，每轮额度更紧、结果更差，越跑越拿不到干净结果。上游额度不是无限的重试资源。

**规则 8.4**：区分「代码缺陷」和「上游额度限制」，并让工具帮你区分。我们的分批脚本会识别 `1135` 并单独归类，避免把额度问题误报成代码问题——这个区分做不好，会浪费大量时间去 debug 根本不存在的 bug。

**规则 8.5**：不要把旗舰模型（`claude-opus-*`）放进默认测试模型集（见规则 2.5）。我们因为这个被卡了 4.5 小时，换成 `claude-sonnet-5` 后同样覆盖 Anthropic 系列的翻译路径，额度压力小得多。

## 九、如果你要对外提供 API（额外注意）

**规则 9.1**：如果实现了 Anthropic / Gemini 的**协议格式**，也要实现它们的**鉴权约定**，否则官方 SDK 开箱即 401：

| SDK | 发送的鉴权头 |
|---|---|
| `openai` | `Authorization: Bearer <token>` |
| `anthropic` | `x-api-key: <token>` |
| `google-genai` | `x-goog-api-key: <token>` 或 URL query `?key=` |

我们就栽在这里：协议做对了，但鉴权门只认 `Authorization`，两家官方 SDK 完全用不了。而自研测试用 `requests` 手工构造头，**从来没走过 SDK 的鉴权路径**——这是个典型的测试盲区。

**规则 9.2**：CORS 预检也要放行这些头（含 `anthropic-version`），否则浏览器端 SDK 被拦。

**规则 9.3**：**用官方 SDK 做兼容性测试，不要只用手工 HTTP。** 手工构造请求永远测不出「SDK 会发什么头」「SDK 怎么解析事件序列」这类问题。我们用官方 SDK 一测，立刻发现了鉴权（P0）、Gemini 流式多发 `[DONE]` 导致解析崩溃、Responses 流式事件序列不完整导致 SDK 抛 TypeError 三个问题——全都是手工 HTTP 测不出来的。

**规则 9.4**：注意各协议的 SSE 终止约定不同。`data: [DONE]` 是 **OpenAI 的约定**，Gemini 官方协议里**没有**这个哨兵——多发它会让 `google-genai` SDK 解析崩溃。转换时别把一家的约定套到另一家上。
