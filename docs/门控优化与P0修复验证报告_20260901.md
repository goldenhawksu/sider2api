## 二、P0 鉴权兼容

### 问题回顾

`authMiddleware` 只认 `Authorization: Bearer`，而 anthropic SDK 发 `x-api-key`、google-genai SDK 发 `x-goog-api-key`——**两家官方 SDK 开箱即 401**。协议格式早已实现，是鉴权门没开。

### 修复

新增 `extractAuthToken()`，依次识别 `Authorization: Bearer` / `x-api-key` / `x-goog-api-key` / `?key=`；CORS 预检放行相应头。

### 生产验证（零额度部分）

```
主页 200 · 模型清单 59 条 · /stats 200

Authorization: Bearer wrong  ->  "Unauthorized: Invalid token"
x-api-key: wrong             ->  "Unauthorized: Invalid token"
x-goog-api-key: wrong        ->  "Unauthorized: Invalid token"
无凭证                        ->  "Missing or invalid credentials. Provide one of:
                                  Authorization: Bearer <token>, x-api-key, x-goog-api-key, or ?key="
```

三种鉴权头都返回 `Invalid token` 而非 `Missing credentials`——证明**头被识别了**，只是 token 不对。

### 生产验证（官方 SDK 真实调用）

| 用例 | 结果 |
|---|---|
| anthropic SDK **原生 `x-api-key`**（非流式） | ✅ `'OK'`，`stop=end_turn` |
| anthropic SDK **原生 `x-api-key`**（流式） | ✅ 15 deltas / 34 chars |
| google-genai SDK **原生 `x-goog-api-key`** | ✅ `'OK'` |
| openai SDK（流式，回归确认） | ✅ 52 chunks / 67 chars / 4.2s |

**三家官方 SDK 现在都能把 `base_url` 一改就接入**，不需要任何手工构造请求头。

## 三、门控优化四项

### 1. 熔断时长跟随上游告知的时间

sider 的 1135 会明说 `Please try again after N minutes`，此前这个信息被丢弃，一律按模型类型硬编码。两个方向都会错：

| 上游实际说的 | 旧行为 | 后果 |
|---|---|---|
| `after 1 minutes`（opus） | 罚 1 小时 | **白白闲置 59 分钟可用额度**（8/31 实测锁死 `claude-opus-4.8` 近 1 小时）|
| `after 117 / 272 minutes`（非 opus） | 罚 1 分钟 | 此后**每分钟撞一次墙**，纯浪费 |

现按上游告知的真实时长熔断，解析不出才回退固定兜底。`isOpusModel` 特判降级为兜底——**不用再猜哪个模型金贵，上游会告诉你**。

### 2. 上游并发闸门（默认关闭）

上游账号实测单并发（10 并发只有 1 个成功）。实现了排队闸门，但**默认 `UPSTREAM_MAX_CONCURRENCY=0` 保持既有行为**。

原因：本项目此前已明确移除进程内全局锁（多实例下无法跨实例保护），并有 `test_image_generation_has_no_process_global_concurrency_lock` 守卫。推翻一个有测试守卫的既有决策，不应在实施中顺手做掉。能力保留，需要时显式开启。

### 3. AIMD 自适应配额

固定 6 次/60s 与上游真实容量无关：串行客户端每次 3～5 秒，一分钟本可做 12～20 次却被限到 6 次。改为连续成功加性放宽（上限 30）、撞 1135/1101 乘性减半（下限 2）。

**生产实测**：

```
同模型连打 gpt-4.1(极短 prompt):
  第1~8次: 200
  第9次:   429  Retry-After=43  "限速策略: 每 60 秒最多 8 次调用。"
```

配额从 6 放宽到 8，第 9 次才被拦——与设计推演完全一致（每 3 次连续成功 +1，n=9 时 count=8 已达 quota=8）。**旧行为第 7 次就会被拦**。响应也正确带上了 `Retry-After`。

### 4. 账号级额度枯竭判定 + 半开探测

1135 首先是模型级的（实测 opus 锁死时 gpt-5.5 正常），但短时多个模型都 1135 就是账号池枯竭，此时不该让请求逐个模型试探。

**半开探测**是必需的配套：冷却期内定期放行一个请求，成功即解除。没有它，冷却期内所有请求都被拦，就永远等不到"已恢复"的证据——那等于把"惩罚过度"的毛病从模型级搬到账号级。这个缺陷是通过「单独跑通过、全量跑失败」的测试污染现象发现的。

## 四、流未读完不 cancel 的连接泄漏（独立修复）

### 问题

各流式路径普遍「提前 `return` 但不 `cancel`」——四个流式 `start()` **每个都是 1 处 cancel 对 5～6 处 return**；图像生成的成功路径也是收够图就 `break`。上游流不 cancel 会让连接一直挂着，**上游很可能仍把该请求算作「进行中」**，对单并发账号尤其不利。

### 修复方式

收口在 `SSELineReader.readLines` 的 `finally`：`readLines` 是 async generator，`for await` 提前 `break`/`return`/`throw` 时 JS 必定调用其 `.return()`，`finally` 保证执行——**一处覆盖全部 10 个读流入口**，比在每个调用点补 cancel 更不容易遗漏。

### 生产验证

| 场景 | 结果 |
|---|---|
| 图像生成（成功路径 `break`，主场景） | ✅ 10.5s，返回真实 CDN URL |
| 流式 + `stop` 参数（走提前 `return` 路径） | ✅ 14 行 / 3.0s |

按 8/31 的教训（连跑四轮，每轮额度更紧、结果更差），**没有继续重跑**。

### `test_rate_limit.py` 的调整

配额拦截 / 模型隔离 / 429 错误格式三项**迁移**到 mock 回归（`test_quota_exhaustion_blocks_and_isolates_by_model`）：

- 原本每例要真打 6+ 次上游，是全套件最费额度的文件
- 它们测的是**门控逻辑**而非上游行为，放 mock 里零额度且更精确
- mock 用固定配额实例（`RATE_LIMIT_QUOTA_MAX = RATE_LIMIT_MAX_CALLS`），不受 AIMD 放宽影响

保留了需要真实上游的两项（603 不触发熔断）。**覆盖没有降低，额度成本显著下降。**
